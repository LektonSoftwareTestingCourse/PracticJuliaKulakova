**Расхождения между источниками перечня эндпоинтов:**

- Спецификация не описывает реализованные в контроллерах и доступные через Gateway: `GET /api/cards`, `PATCH/DELETE /api/cards/{pan}`, `POST /api/cards/{pan}/reserve|rollback`, `POST /api/cards/bulk-update`, `GET /api/transactions/export`, `GET /api/dashboard/charts`, `POST /api/internal/rollback` (authorization), `GET /api/simulator/merchants`, `POST /api/simulator/merchant/fee`, `POST /api/simulator/terminal/start-continuous|stop`.
- `WS /ws/transactions` из спецификации не маршрутизируется Gateway (только напрямую logger) и не является синхронным HTTP-контрактом — вне области.
- В спецификации у `POST /api/cards` заявлен `409` (дубликат PAN), в контроллере такого исхода нет — PAN генерируется сервером.
- `search` в реализации поддерживает фильтры `issuerId` и `mcc`, которых нет в таблице параметров спецификации.

## 2. Бизнес-отказы

Код и причина проверяются совместно в каждом тесте. Через Gateway все отказы возвращают HTTP 200 с `status=DECLINED` (см. §4, п.4); через прямой вызов authorization — HTTP-статус из `AuthControllerImpl`.

| Исход                           | Код  | Причина                   | Путь достижения                                    | Способ подготовки данных                         | Статус |
|---------------------------------|------|---------------------------|----------------------------------------------------|--------------------------------------------------|--------|
| Одобрение                       | 00   | — (null)                  | Gateway → switch → authorization → reserve         | `POST /api/cards` с балансом 10 000 000          | ✅      |
| Карта не найдена                | 14   | CARD_NOT_FOUND            | authorization → card-management 404                | случайный PAN с известным BIN 400000, карты нет  | ✅      |
| Неизвестный BIN                 | 14   | CARD_NOT_FOUND            | switch (RoutingService), до authorization          | PAN с BIN 999999 (нет в `switch.bin-routing`)    | ✅      |
| Карта заблокирована             | 05   | CARD_BLOCKED              | проверка статуса в authorization                   | `PATCH /api/cards/{pan}` → BLOCKED               | ✅      |
| Карта неактивна                 | 05   | CARD_INACTIVE             | проверка статуса в authorization                   | `PATCH` → INACTIVE                               | ✅      |
| Карта просрочена (статус)       | 54   | CARD_EXPIRED              | проверка статуса в authorization                   | `PATCH` → EXPIRED                                | ✅      |
| Карта просрочена (дата запроса) | 54   | CARD_EXPIRED              | `expiryDate.atEndOfMonth() < transmissionDateTime` | ACTIVE-карта + `transmissionDateTime=2099-01-01` | ✅      |
| Недостаточно средств (сумма)    | 51   | INSUFFICIENT_FUNDS        | `amount > availableBalance` в authorization        | карта с балансом 1 000, amount 5 000             | ✅      |
| Недостаточно средств (баланс)   | 51   | INSUFFICIENT_FUNDS        | то же поле, но состояние карты нулевое             | карта с `initialBalance=0`                       | ✅      |
| Превышен дневной лимит          | 61   | EXCEEDS_AMOUNT_LIMIT      | `upsertLimitUsage` (лимит за сутки)                | dailyLimit=1 000, две транзакции по 600          | ✅      |
| Превышен месячный лимит         | 61   | EXCEEDS_AMOUNT_LIMIT      | `upsertLimitUsage` (лимит за месяц)                | monthlyLimit=1 000, dailyLimit большой           | ✅      |
| Отказ валидации Gateway         | —    | HTTP 400 VALIDATION_ERROR | TransactionValidationFilter, до маршрутизации      | невалидное поле запроса                          | ✅      |

**Один исход — разные пути.** `CARD_EXPIRED (54)` достигается и состоянием карты (статус EXPIRED), и данными запроса (будущая `transmissionDateTime` при ACTIVE-статусе) — проверены оба пути (`TransactionDeclineApiTest`). `CARD_NOT_FOUND (14)` достигается двумя разными маршрутами: отсутствие карты в card-management (отказ формирует authorization) и неизвестный BIN (отказ формирует switch, запрос до authorization не доходит). Пути различаются точкой формирования ответа при одинаковых наблюдаемых коде и причине — различие зафиксировано комментариями в тестах и данной таблицей.

Вне покрытия: `SERVICE_UNAVAILABLE (96)`, `RESERVATION_FAILED`, `DB_UNAVAILABLE` — требуют остановки контейнеров/БД, что относится к модулю 6 (интеграционное тестирование); `INSUFFICIENT_FUNDS` через 402 от `reserve` (гонка между проверкой баланса и резервированием) — не воспроизводится детерминированно через API без прямого вмешательства в состояние.

## 5. Обоснование достаточности

**Выделенные классы входных данных и подтверждение полноты:**

1. *Валидация Gateway* — классы построены по каждому правилу `TransactionRequestValidator` (единственный источник правил валидации на входе): обязательность (11 полей), формат (mti, pan, mcc), длина (pan 15/16/17, currencyCode 2/3/4, mcc 3/4/5), знак (amount -1/0/>0), формат даты, целостность тела (битый JSON, пустое тело). Полнота подтверждена построчным покрытием кода валидатора: каждому `throw` соответствует минимум один тест.
2. *Бизнес-отказы* — классы по исходам `DeclineOutcome`, достижимым через API без остановки сервисов (11 из 13; SERVICE_UNAVAILABLE/DB_UNAVAILABLE/RESERVATION_FAILED требуют управления инфраструктурой — модуль 6). Для исходов с несколькими путями достижения покрыты оба пути (CARD_EXPIRED, CARD_NOT_FOUND, INSUFFICIENT_FUNDS).
3. *Поиск/пагинация* — каждый параметр `TransactionFilter` (pan, status, dateFrom, dateTo, merchantId, declineReason, limit, offset) покрыт отдельно; границы limit 0/1/500/501 и offset -1/0; попарные комбинации (pan+status, merchantId+limit/offset, pan+dateFrom/dateTo, pan+declineReason); пустая выборка; некорректная комбинация (dateFrom > dateTo).
4. *Повторная доставка* — все исходы `POST /api/internal/log`: новая запись (201), повтор с идентичными данными (200), повтор с расхождением данных при том же ключе (409), невалидное тело (400, 5 вариантов).
5. *Асинхронные эффекты* — появление (транзакция через Gateway становится доступной в search/recent/CSV — Awaitility `atMost(20s)/pollInterval(500ms)`) и отсутствие (запрос, отклонённый валидацией, не попадает в хранилище; отклонённая транзакция не резервирует средства — Awaitility `during(3s)`, условие должно оставаться истинным всё окно).

**Осознанно вне покрытия:**

- `WS /ws/transactions` — не синхронный HTTP-контракт, не маршрутизируется Gateway (область модуля 6).
- HTTP 429 (rate-limit Gateway) — требует >100 запросов/с с одного IP; в общем CI-прогоне даёт нестабильность. Контракт задокументирован по коду `TransactionRateLimitFilter` (429 + `Retry-After: 1` + тело `RATE_LIMIT_EXCEEDED`).
- HTTP 503 и circuit breaker — требуют остановки контейнеров (модуль 6, интеграционные тесты); контракт 503 описан по коду `DownstreamErrorFilter`.
- `POST /api/cards/{pan}/reserve|rollback`, `bulk-update`, `POST /api/internal/rollback`, bin-issuer CRUD, `merchant/fee`, `start-continuous/stop` — отсутствуют в спецификации; эффект reserve/rollback покрыт косвенно (баланс карты после одобрения/отказа, rollback-путь — через исходы авторизации). Прямое тестирование внутренних операций card-management выходит за границы «контрактов из трёх источников».
- Прямые эндпоинты bin-lookup и notification-service — не доступны через Gateway, покрыты существующим модулем `e2e-tests` (модуль 6).

**Изоляция и воспроизводимость:** каждый тест создаёт собственные данные (уникальные PAN/STAN/merchantId/terminalId/UUID через `TestData`), подготовка состояния — только через API (`CardApi`, `SearchApi.storeTransaction`); порядок запуска не влияет на результат; постоянные идентификаторы между тестами не разделяются.

## 7. Порядок запуска

```bash
# 1. Поднять стек СМП
cp .env.example .env        # Windows: copy .env.example .env
docker compose up -d        # дождаться healthy всех контейнеров

# 2. Запустить API-тесты одной командой
mvn -f services/pom.xml -P api-tests test

# Точечный запуск класса/теста
mvn -f services/pom.xml -P api-tests test -Dtest=TransactionDeclineApiTest
mvn -f services/pom.xml -P api-tests test -Dtest="TransactionDeclineApiTest#unknownBinDeclinedBySwitch"

# Переопределение адресов (если порты отличаются от .env.example)
mvn -f services/pom.xml -P api-tests test -Dgateway.baseUrl=http://localhost:8080 -Dlogger.baseUrl=http://localhost:8088
```

**CI:** job `api-tests` в `.github/workflows/practice-run.yml` — запускается через Actions → Run workflow → practice `5` (вместе с e2e-tests): собирает образы, поднимает `docker compose`, ждёт healthy, выполняет `mvn -f services/pom.xml -P api-tests test`, при падении печатает логи контейнеров.
